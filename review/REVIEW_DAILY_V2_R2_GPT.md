其他：先解 U1，並先把 QA gate 與規則治理方式重構，再跑 140 張；不是先重寫全部 prompt 規則。

## 二、31 條稽核規則

### 2-1 有沒有互相矛盾的規則？

**結論：目前我沒有看到會讓同一個合法 prompt「邏輯上無解」的硬矛盾，但有明顯的重疊、耦合與層級混用；這比真正互斥更危險。**

具體分三類：

1. **24（四肢預算）與 25（手部預算）高度重疊。**
   - 24 是「身體資源佔用」：姿勢與 micro 一共用了幾隻手／臂。
   - 25 是「持握物數量」：有幾件東西被手拿著。
   - 兩者概念上不是完全相同，所以不應直接刪掉一條；但現在兩條都靠局部正則從自然語言猜語意，會產生同一件事被雙重攔截、或兩條都漏掉的情況。
   - 建議把它們合成同一個「limb occupancy」結構化檢查：先把 pose/micro 轉成 `left/right/one/both/none` 或至少 `limb_cost`，再由一個規則算總資源；不要讓兩套 regex 各自猜。

2. **15（full_length 必須動態）與 19（禁止懸空／手肘外翻）沒有邏輯矛盾，但形成狹窄的姿勢白名單。**
   - 目前 `DYNAMIC_POSE` 實際只認 `leaning back / mid-stride / turned back over her shoulder / half-seated` 四類。
   - 這不是「全身不能直立」的語意規則，而是「全身只能用這四個字串之一」的實作規則。
   - 所以真正問題不是 15 和 19 互斥，而是 15 已經從品質原則退化成字串白名單，長期一定過擬合。

3. **R3 的場景↔光線規則也有同類風險。**
   - `SCENE_LIGHT` 用場景關鍵字決定允許的光線集合，本質是 heuristic，不是物理約束。
   - 例如同樣是 cafe、station、bar，實際能成立的光型很多；若以關鍵字硬綁，未來會阻擋合理新場景。

所以我不建議把問題描述成「31 條裡有沒有兩條互相打架」而已。更準確的說法是：**31 條把 schema validation、lint、風格偏好、模型經驗法則混成一個 hard-fail gate。這個架構已經開始壞。**

我建議把規則拆成三層：

- **A. Deterministic invariants（硬擋）**：資料本身若矛盾一定錯，例如 continuity_from 對不上 outfit、非鏡面格明寫 phone/camera、欄位空白、同穿搭提到不存在的衣物部件、明確 limb budget 超額。
- **B. Prompt lint（警告或需人工確認）**：例如場景首名詞、黑名單措辭、全身動態姿勢、場景↔光線 heuristic。這些不應全部用 `SystemExit` 當成真理。
- **C. Model-behaviour hypotheses（不能靠 audit 宣告通過）**：例如「K6 會出長影」、「腰線字串會讓衣服有形」、「背景路人句能避免撞臉」、「waist_up 會控制 framing」。這些只能靠生成後 QA / A-B test 驗證，不能因 prompt 含某字串就算通過。

### 2-2 有沒有對單一次失敗過度擬合？

**結論：有，而且已經出現明確證據。最典型的是 12；另外 15、16、18、19、30 也有不同程度的過擬合。**

規則 12「場景首名詞不得是檯面」本質上是在修 `She is in {scene}` 這個模板介面，而不是在修生成模型。

`She is in a rural post office counter` 出錯的真正不變量是：**`scene` 必須是一個能合法接在 `She is in ...` 後面的 location phrase。**

現在把 `counter/table/worktop/vanity` 列成黑名單，只是在記住那一次事故。未來若出現 `a checkout lane`、`a reception desk`、`a ticket booth counter`，還會再加 regex。這就是典型 rule accretion。

所以 12 應該移回資料／模板層解決，例如把欄位拆成：

- `location = "a rural post office"`
- `scene_details = "a franking machine on the worktop..."`

模板固定輸出 `She is in {location}, with {scene_details}.`

這樣一次消掉整個錯誤類別，不需要永久保留「檯面黑名單」。

同理：

- 15 的真正原則是「全身照不能產生呆板柱狀構圖」，不是只能四種 pose 字串。
- 16 的真正原則是「衣服要符合已定的時髦標準」，不是 `apron/fleece/...` 這幾個 token 永久有罪。
- 18/19 是從幾次失敗提取出的語言風險詞，適合當 lint，不適合當 universally-invalid grammar。
- 30「裸否定句」有跨案例證據，但仍應檢查語境，而不是只要出現 `no mirror` 就 hard fail。

**判準：一條規則若只是在禁止某個字串，而不是表達可泛化的不變量，就優先視為過擬合候選。**

### 2-3 黑名單式規則會不會綁死正常寫法？

**結論：會，而且六次 regex 誤判已經足以證明這不是理論風險，而是正在發生的維護成本。**

六個案例（`crop shirt`、`very short navy pleated skirt`、`low cowl neck`、`short pencil skirt`、`in her free hand`、`waist seam`）說明目前的系統在做的是「自然語言 parser 的工作」，但用的是不完整 regex。

這種架構有兩個後果：

1. **false positive 會讓作者為了通過稽核而改寫本來好的 prompt。** 最後 prompt 會逐漸為 validator 最佳化，而不是為模型最佳化。
2. **false negative 仍然存在。** zoey D4 的 `both elbows + basket on one arm` 就是例子；所以「規則越多」沒有換到可信的 coverage。

我的建議不是把所有黑名單刪掉，而是改治理方式：

- 黑名單預設降成 lint，只有「已跨多個樣本重現，而且誤殺率可接受」才升 hard fail。
- 每條 regex 必須有正向與反向 regression cases；不能只測「壞字串會被擋」，也要測一組「正常字串不會被擋」。
- 每條規則記錄 `origin / scope / evidence / false-positive examples / owner / status`。單次事故先標 `experimental`，多次重現再升 `stable`。
- v1→v2 重寫時丟掉三個 guard，說明還需要一個**規則清單的 regression test**：新 generator 必須證明所有 stable invariants 仍在，而不是靠人工記憶。

這裡我認為最值得改的，不是把 31 條減成 20 條，而是**停止「每出一張壞圖就永久新增一條 hard-fail regex」這個累積模式。**

## 三、140 張再挑的策略

### 3-1 140 張再挑在什麼條件下是錯的？

**結論：當缺陷是「系統性且高覆蓋率」或「QA 不可靠到無法穩定辨識廢片」時，140 張再挑是錯的；隨機、低比例、容易目視的缺陷才適合靠 oversampling 吸收。**

我會把缺陷分四類：

| 類型 | 適不適合 140 張再挑 | 原因 |
|---|---|---|
| 隨機生成瑕疵，例如偶發手指、偶發小構圖偏差 | **適合** | 多跑可以用成功樣本覆蓋失敗樣本 |
| 系統性 prompt/model failure，且影響大量格 | **不適合** | 多跑只是在複製同一錯誤分布 |
| 不容易被 QA 看出的隱性缺陷 | **不適合，除非 QA 先補強** | 跑 140 張後仍可能把廢片挑進 100 張 |
| 只影響整批多樣性、單張仍可用 | **可接受，但要先估容忍度** | 可透過事後配額/挑選控制，不一定值得繼續微調 |

以目前資料來看：

- **U1 是典型「不能直接 oversample」的缺陷。** 影響 59/100，而且舊 §9 已被實證打穿；新句尚未實測。若 Soul 的身份條件化真的會污染任何可見背景臉，那 140 張只會生更多撞臉。
- **第三隻手本來也屬系統性，但現在 prompt-side limb allocation 已找到可泛化原因，且可以 deterministic audit；它適合先修完後再靠少量 residual failure 用 oversampling 吸收。**
- **U2 framing 屬於「單張可用、整批分布變差」；不一定值得阻擋 140 張。** 真正處理方式可以是在 140 張中按實際 framing 分桶挑 100，而不是繼續追求 prompt 100% 遵守指定 framing。
- **U3 K6 是局部、可預測的場景相容性問題。** 既然已連續兩次在遮蔽建築場景失效，應改掉那一類格的 K6，不需要再為整個系統多跑驗證輪。

最重要的是：目前「再跑幾張小樣」的邊際資訊價值已經下降。前四輪確實在找根因；但第 5、6 輪開始出現的是**QA 本身漏判**。如果 QA 方法不變，再做第 7、第 8 輪，可能只會再次得到「我判 PASS → 使用者找到漏項」。這就是我認為現在已經進入過度迭代的地方。

因此我不建議「先把 prompt 通過率磨到接近 100% 再大量跑」。我建議改成：

1. 先修掉 **U1 這個高覆蓋系統性風險**；
2. 同時修 QA gate；
3. U1 用非常小的定向樣本驗證，不再做全面小批次；
4. U1 若過，直接進 140 張＋事後挑選。

### 3-2 QA gate 要怎麼改，才不會再發生「我說乾淨但其實裁錯區」？

這是我認為本輪最重要、而且目前文件沒有真正解決的一點。

**生成前 audit 與生成後 QA 必須拆成兩個獨立系統。** 現在 31 條 audit 很完整，但它只能證明「文字符合你目前的規則」，不能證明圖乾淨。

生成後 QA 至少要固定成 checklist，而不是自由觀看：

1. **anatomy sweep**：四邊＋雙手／雙臂／腿部逐區掃描，不能只裁「我以為有問題的地方」。
2. **background identity sweep**：所有可見背景頭部區域都要檢查；自動工具只能報陽性，0 不得作為 PASS 證據。
3. **framing**：指定 vs 實際記錄，不必都 hard fail，但要累積分布。
4. **outfit silhouette / pose**：這是使用者在第 5 輪抓到、而你原 QA 沒列的主觀品質維度，必須列成顯式欄位，而不是最後憑「可用」二字總結。
5. **lighting / scene adherence**：記錄偏差但分 hard/soft。
6. **PASS 必須建立在 checklist 全部走完，而不是「看過原圖」或「裁過某區」。**

更進一步，我建議把「驗證 prompt 修法」和「驗證整張可用」分開：一張圖可以證明某修法生效，但同時仍因另一個缺陷成為廢片。`VERDICT_daily_v2_reshoot4.md` 就把「露出、腰線、姿勢修法成立」與「整張乾淨可用」混成同一個 PASS，才會出現後來被第三隻手推翻的情況。

所以之後應該寫成兩個 verdict：

- `hypothesis verdict`: 這次要驗的變因有沒有生效？
- `asset verdict`: 這張圖整體能不能進素材庫？

兩者不能再用同一個「PASS」代替。

## 四、U1–U4 哪些必須在 140 張之前解決

### 4-1 U1 背景路人撞臉

**結論：必須先解，而且是唯一明確阻擋 140 張的生成端問題。**

理由：

- 影響 59/100，覆蓋率太高。
- 舊 prompt 防護已實證失效。
- 已污染先前被判通過的圖，證明 QA 也不容易第一眼發現。
- 新修法改變幅度大（人數、角度、可見臉、失焦程度），但尚未做任何 Soul V2 實測。

建議不是再跑一輪「完整驗證組」，而是只做 **4–6 張 U1 定向測試**，全部選最容易出背景臉的場景，且 QA 專門掃背景。若新句能讓可見臉基本消失，就停止繼續磨；不要為了把 4/4 變成 8/8 再開新輪。

### 4-2 U2 framing 控制弱

**結論：不必先解到 prompt 遵從率很高，可以帶著這個已知弱點進 140 張。**

理由：它目前主要傷害的是「100 張集合的多樣性」，不是單張品質。

如果跑 140 張，本來就有 40 張 buffer；可以把實際 framing 納入選片配額，例如最後 100 張按實際胸上／腰上／三分身／全身分桶選，而不是只看原本 slot 標籤。

只有在 140 張試跑後發現實際 framing 幾乎全部塌到同一兩類，才值得回頭研究 prompt 控框。現在繼續用 0.48、0.48 一輪一輪試景別措辭，資訊價值偏低。

### 4-3 U3 K6 在遮蔽建築場景失效

**結論：要在跑前修資料，但不需要再實測。**

已經同一場景類型連續兩次不生效，足以把「K6 適用於遮蔽柱廊」這個假設否掉。這不是值得再開一輪生成驗證的問題。

做法：把受遮蔽建築場景的 K6 換成已知可成立的 open shade / front-side window / bounced-light 類型；K6 留給真的有直射低角度陽光條件的場景。這應視為資料映射修正，不是新增 regex。

### 4-4 U4 撞臉篩檢程式只做一半

**結論：不必修到「能證明沒撞臉」才跑 140 張；但 QA 流程必須明確承認它只能抓陽性。**

README 已經把能力邊界寫得很清楚：抓到就是陽性，抓不到不能證明乾淨。這種工具即使把分塊去重 bug 修好，recall 仍大約只有目視可見臉的一半，所以它本質上不可能取代人工背景 sweep。

因此：

- 可以修去重 bug，因為能增加陽性召回，值得做；
- 但**不要把「把 U4 做完」設成 140 張的前置 gate**，否則會掉進另一個過度迭代洞；
- 真正的 gate 是 U1 新 prompt 是否讓「可見背景臉」大幅下降，以及人工 QA 是否固定檢查背景。

## 最終方法判斷

**你現在確實已經開始過度迭代，但不是因為「6 輪很多」或「31 條規則很多」。**

真正的判準是：前幾輪每花 0.24–1.2 credits，都換到一個新的高覆蓋根因，這些迭代有價值；但最近兩輪已經變成**生成結果存在硬缺陷，而同一個 QA 流程仍宣告整批通過**。此時再用相同方法跑更多小批次，已經不能顯著提高可信度。

目前應該停止的不是「所有修正」，而是這個循環：

`生成少量 → Claude 自由觀看 → 宣告 PASS → 使用者找漏項 → 再加一條 regex → 再生成少量`

改成：

`規則分層治理 → U1 單點驗證 → 固定 checklist QA → 若 U1 過就直接 140 張 → 依實際品質與 framing 分桶挑 100`

這樣才是從「追求 prompt 在生成前看起來完美」轉成「用有限規則擋系統性災難，再用 oversampling 處理生成模型的隨機性」。
