### 問題 1：5 張高多樣性是否足夠

**結論：5 張高多樣性有可能訓練成功，也可能比 13 張近重複圖更能泛化到新場景，但不能把它視為等效替代；五張改善的是「覆蓋」，十三張提供的是「重複觀測」，兩者解決不同問題。**

#### 1a. 5 張能不能等效於 13 張

張數不是 endpoint 的硬門檻，否則 5 張不會被接受；真正未知的是五張能否達到本專案要求的身分穩定度。這批五張的場景、服裝、光線與景別分散，對避免服裝／背景烙印及測試泛化有利；但「每張所有條件都不同」也有一個代價：模型只在每種角度和光線下看過她一次，較難把固定的臉部幾何與暫態的妝髮、表情、透視、光影分離。

過去 12–13 張即使低多樣性，仍會反覆提供眼距、鼻口比例、下顎、年齡感等共同訊號。那種冗餘不是完全浪費。尤其本批五張都由同一個 Reference Element 衍生，場景雖獨立，身分證據仍是同源的；共享的 element 偏差或生成器美化也可能被五張一起放大。

因此正確判定是：**5 張足以做低成本實證 pilot，但在這個帳號上尚未被證明足以量產 19 位。** 不能因為五張「多樣性高」就直接推論等效於既有 12–13 張，也不能在沒有訓練結果前直接判定必敗。

#### 1b. 如果五張不足，缺什麼、補幾張

**缺的首先不是更多新場景，而是受控冗餘與橋接圖；若 5 張 pilot 未通過，固定補 4 張到 9 張。** 四張都必須仍是可發布生活照，但做成同一段自然生活小系列，讓模型在較一致的服裝、妝髮、背景與柔和日光下重複看到身分：

1. **正面胸上**：自然表情、canonical 髮型、妝感最低、雙眉與完整下顎清楚。
2. **左 front-three-quarter 胸上**：約 25–40°，與第 1 張同服裝、同地點、同光線。
3. **右 front-three-quarter 胸上**：與第 2 張鏡像對稱的資訊條件，仍維持同服裝與光線。
4. **近正面腰上或全身橋接圖**：臉仍可辨識，肩、胸、腰、臀比例可讀，服裝合身但日常；與前三張同一時段拍攝。

這四張的目的不是增加第四、第五個支柱，而是建立「同一人、同一狀態、不同視角」的共識，並把臉部證據接到身材證據。若失敗只發生在身材而臉 6/6 穩定，四張中可把第 2、3 張改為一張腰上、一張 45° front-oblique 全身；若臉漂移，維持上述三張 face-dominant 配額。

不要先為 19 位全部補圖。只有 pilot 證明五張不夠，才用同一個 `+4 → 總數 9` 協定補其餘尚未訓練的人；不要每位自行決定補 2、3、7 張，否則無法比較。

### 問題 3：操作協定

**結論：現有協定方向正確，但還缺少帳號排他鎖、不可變輸入 manifest、明確版本命名，以及「有扣款或有角色記錄就禁止第二次 train」的分支；19 位絕對不要並發送訓。**

#### 3a. 建議的完整協定

每一位依下列順序執行，未通過當步就停止：

1. **取得帳號排他時段**：確認其他操作者沒有上傳、生成或訓練任務；本輪只留一位操作人。
2. **建立 immutable manifest**：記錄 persona、訓練版本、檔名、檔案 SHA-256、尺寸、檔案大小與預期張數。逐張核對沒有重複、錯人、鏡面第二張臉或損壞檔。
3. **先查角色清單**：確認沒有相同 persona＋版本的 `ready`、`training` 或 `queued` 記錄；名稱使用可追蹤版本，例如 `wanyin-jiang-soul-v1-5img-20260907`。
4. **記錄送出前狀態**：餘額、最新 transaction 時間／游標、角色清單快照。
5. **just-in-time 重新上傳這一位的圖片**：逐張取得新 `media_id`、上傳、`media_confirm`；把 `file_sha256 → media_id` 寫回 manifest。不要先把 19 位 media ID 混在一張手工清單。
6. **train 參數顯式固定**：`action='train'`、唯一版本名、`type='soul_2'`、`images=[已確認的 media_id]`。送出前再次核對陣列張數及第一／最後一個 ID。
7. **只呼叫一次**，立即保存完整回應、呼叫時間與任何返回的 `soul_id`。
8. **立刻做三重核對**：transaction、`action='list'`、若有 ID 再做 `action='status'`。成功受理的必要證據是角色記錄與 ID；`Soul ID -25` 是費用證據，但不能單獨代替角色記錄。
9. **進入狀態機**：`queued/training` 只輪詢，不重送；`ready/completed` 才進驗證；`failed` 保存 fail reason 並停；工具報錯則走下方不確定狀態處理。

#### 3d. 第 N 位失敗如何續跑

已經 `ready` 的 N−1 位是獨立 Soul ID，第 N 位失敗不會回滾或污染它們；但失敗可能代表帳號／endpoint 的系統性狀態，所以不能立刻送第 N+1 位。

安全續跑以 manifest 為準，不以迴圈計數為準：

- `ready/completed`：永久跳過，不重訓。
- `queued/training`：只查狀態，不重送。
- `charged/no record`、429、工具錯誤：整批暫停，先核帳與排除平台狀態。
- `failed` 且有角色 ID：保存失敗原因；確認平台是否要求建立新版本後再處理該位。
- `not submitted`：平台恢復、餘額對平後，從第一個未送出的 persona 繼續。

### 問題 4：送出前遺漏項

**結論：在第一筆 train 前還要補七個 gate；全部通過後才送 wanyin pilot。**

1. **防串人 manifest。** 96 張最嚴重且最便宜可防的事故不是少一個角度，而是某位陣列混入另一位的 media ID。每位產生獨立 machine-readable manifest，包含 SHA-256、media ID、persona、版本與順序；train 前由另一個步驟重新由檔案 hash 對回 ID，不手工複製 UUID。
2. **檢查「高多樣性」沒有犧牲身分解析度。** 全身圖雖通過整體目視 QA，仍要確認原始檔可正常解碼、方向正確、臉部可被偵測且放大後眼鼻口沒有糊掉；五張中至少三張是 face-dominant，兩張全身的臉也必須可與 master 核對。若某位只有兩張真正可讀的臉，帳面五張不算五個有效身分觀測，應在 pilot 結論前先補圖。
3. **檢查共同生成偏差。** 把每位五張裁臉排成接觸表，遮掉背景、服裝與髮型，再看是否共享同一個不自然妝感、固定表情、磨皮紋理或 element 造成的年齡偏差。場景多樣不代表身分訊號多樣；若五張其實是同一張 element 臉的近複製，Soul 可能很穩定但泛化差。
4. **驗證不得洩題。** 六張 held-out prompt 不得包含完整五官答案、Reference Element、訓練場景或訓練服裝；否則測到的是 prompt／element，不是 Soul。驗證前先把 prompt 和通過門檻鎖進 manifest，看到結果後不得改門檻或補抽。
5. **版本與不可逆性。** 訓練名稱要帶 persona、版本與 `5img`／`9img`，保存輸入 manifest、回應、transaction 與 soul_id。`ready` 後也先標成 `trained_unvalidated`，六張通過才升為 `approved`；不要因平台顯示 ready 就覆寫既有可用 Soul 或把新 ID發布到正式流程。
6. **預算 reserve。** 475 不是完整上限，還要保留兩位 pilot 驗證、可能的 wanyin 九張重訓、其餘驗證及異常扣款。開始前先圈存至少 `475 + 14 + 30 = 519 credits`；任何三人批次實扣超過預期 75 credits，或出現一筆無產出的費用，就觸發停損對帳。
7. **先確認驗收責任人與一次性決策表。** 六張驗證由同一位使用者用同一張 contact sheet 盲評；結果只允許「通過／五張不足，補四張／管線錯誤」三種。不要用「再生一張看看」作第四種答案。

最終 go/no-go：先完成上述 gate，只送 wanyin；若六張通過，再送一位碰撞風險 pilot；兩位都通過才開始其餘 17 位。任何 pilot 失敗都先停在該位，不能為了已經備齊 96 張而讓沉沒成本推動剩餘 450 credits 的支出。
