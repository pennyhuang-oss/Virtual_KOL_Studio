## 🔴 生成節奏與逐件覆核（2026-08-28 Penny 定，最高優先）

| 規矩 | 內容 |
|---|---|
| **一次只跑兩張** | **絕對不要一次跑 16 張。**每次生成 = **一件 spec × 2 張**，看完再跑下一件 |
| **每一段 prompt 送出前都要覆核** | 不是「沒把握才送」——**是每一段都要**。ChatGPT 說不行就改，改完再送 |
| **覆核可以批次、生成不可以** | 為了少讓 Penny 轉傳，一次覆核請求可以放**數件**的 prompt；但**生成仍然一件一件、兩張兩張跑** |

> 這兩件事分開：**覆核批次化是為了省 Penny 的轉傳次數；生成兩張兩張是為了每一步都看得到結果。**
> 不要因為覆核一次過了四件，就把四件一起丟去生成。

## ⚠️ 2026-08-28 流程修正：ChatGPT 只讀一個檔案，不要爬 repo

**起因**：ChatGPT 的 GitHub 連接器把整個專案背景讀進來，**一次就耗掉使用者方案內 5 小時的用量**。
它只做檢核、不規劃也不執行，用量卻比執行方還高——不合理。

**問題不在用 GitHub，在於爬整個 repo。**所以流程是：

| 誰 | 做什麼 |
|---|---|
| **Claude** | 改完檔案後，把 `review/REVIEW_REQUEST.md` **整份重寫**成自足的請求：改前／改後全文、背景速查、具體問題、預留好的回覆填空區 |
| **Penny** | 傳一句話給 ChatGPT，指定它讀那一個檔案 |
| **ChatGPT** | **只讀那一個檔案**，把答案填進檔案裡的回覆區，commit 回同一個分支 |
| **Claude** | `git pull`，讀回覆，謄進 `review/restaurant-b1/LEDGER.md`，執行，更新狀態 |

**檔案開頭必須有讀取範圍限制的警語**，寫明只讀這一個檔案、不要瀏覽目錄，
並說明為什麼（用量問題）。回覆區要**預先建好填空欄位**，它才不用自己排版、也不會去動別段。

### 🔴 送生成前必須通過覆核指紋閘門（2026-08-29 建立）

**規則：`python3 tools/approval_check.py` 顯示「已覆核」的件才可以送生成。**

「未覆核」或「改過字」的一律不得送測，**即使覆核在別的輪次核可過其中的片語**。
片語被核可 ≠ 整段被核可——組裝後的完整 prompt 必須被看過整段。

覆核通過後才登記指紋：
```
python3 tools/approval_check.py --stamp YG-06,LG-05 "R12 逐件 PASS"
```

> **這個機制在 R7 Q5 就被建議過**（「最好為每件保存 prompt 版本或內容雜湊，
> 避免後續悄悄改字後仍沿用舊核准」），**我一直沒做**。
> 沒做的後果是 LG-01：R11 只裁決了片語層級的還原，組裝後的完整 prompt 沒有人看過整段，
> 我就直接送生成了——那是我自己的認定，不是覆核給的授權。

### 🔴 每一份覆核請求都必須放「對標小雪莉」那一段（2026-08-29 Penny 指出）

**這是一個已經造成實害的缺口。** R7、R8a、R8b 三輪、13 段 prompt 的逐件覆核，
**一次都沒有告訴 ChatGPT 這個專案要對標 `COMPETITOR_sherry_digitalp510.md` 的分析。**
它一直在檢查「規格有沒有矛盾、物理成不成立、驗收得出來嗎」，
**沒有任何一輪在檢查「這看起來像不像一個真人的帳號」**——
結果就是 21 件裡 11 件手停在臉旁、16 件正面看鏡頭，全部通過覆核。

**每一份 `REVIEW_REQUEST.md` 的標頭都要固定包含以下這段，不可省略：**

```
## 這個專案要對標的帳號（每輪都附，請一併用這個角度檢查）

競品 @sherry_digitalp510（小雪莉）是全 AI 生成、公開自承虛擬人的 IG 帳號，
57 萬追蹤。我們已對它做過完整拆解，結論如下——請在逐件判定之外，
**額外用「這則看起來像不像真人的日常」這個角度檢查**：

1. 打光要寫物理路徑，不是品質形容詞：光從哪個具名物體來、被哪個具名表面
   反射回臉上、畫面哪一區因此被犧牲
2. 曝光一定有一邊被犧牲。真實相機一次只能對一個亮度測光，兩邊都保住＝假
3. 一個畫面裡永遠有兩個色溫（適用於真的有兩個光源的場景）
4. 公共場景一定有背景路人。空景的公共場所是最強的合成訊號
5. 視角要混合：自拍／朋友他拍／背後跟拍／俯拍大量交替
6. 框架物入鏡（門框、窗框、簾、柱子）製造天然暗角並合理化光線方向
7. 地點要有 C 級（完全不美的日常：超商、賣場、路邊、候車亭）。
   純 A 級嚮往感讀起來像型錄
8. 姿勢、髮型、微物件每則都在換。**永不重複的節奏本身**才是真實感來源
9. 不要寫 grainy／muddy／degraded——畫質仍要清晰。
   「畫質好」不等於「每一處都曝光均勻」
```

### 🔴 轉傳訊息要可以直接複製（2026-08-29 Penny 定）

每次產出覆核請求，**除了檔案本身，還要在回覆裡附一段可以整段複製、直接貼給 ChatGPT 的訊息**。
不要寫成敘述句叫 Penny 自己組。訊息要用程式碼區塊包起來，內容至少含：
只讀哪一個檔案、不要瀏覽目錄、答案填在哪一段、不要改問題本文、填完 commit 回哪個分支。

### 產出覆核請求的規矩（給 Claude）

1. **自足**：ChatGPT 不該需要開任何其他檔案。要它判斷的文字，一字不漏貼進去
2. **附最小背景**：固定的「已驗證結論」速查表每次都附，它才不用回頭查證
3. **改前／改後都要有**：只給改後的版本，它無法判斷改動是否解決了原問題
4. **問題要具體且有限**：三到五題，每題是一個可以判斷對錯的東西，不要問「還有什麼問題嗎」
5. **短**：目標 8KB 以內。超過就是背景塞太多，該砍
6. **回覆區預先建好**：每題留「判定／理由／建議改法」三欄
7. **明寫不要改其他段落**：`Claude 的看法` 與問題本文是原始紀錄，被改掉就失去對照價值

## 主檔案：`review/restaurant-b1/LEDGER.md`

**一個檔案就好，不要再每輪開新檔。**
`review/restaurant-b1/LEDGER.md` 是一張活的議題表，每一項有固定編號與狀態。

### 狀態流

```
🔵 OPEN        Claude 提出，等 ChatGPT 判定
🟡 ANSWERED    ChatGPT 已判定，等 Claude 執行
🟢 DONE        Claude 已執行完畢
⚪ PARKED      雙方同意暫緩（要寫暫緩到什麼時候／等什麼條件）
🔴 DISPUTED    兩邊看法不同，需要用實測解決（要寫怎麼測）
```

### 給 ChatGPT 的編輯規則

1. **只改你那一欄／那一段**（`### ChatGPT 判定`），不要改 `### Claude 的看法`
   —— 那是提出當下的原始紀錄，改掉就失去了對照價值
2. **改完把狀態從 🔵 改成 🟡**（或 ⚪ / 🔴）
3. **不要刪除已 🟢 DONE 的項目**，往下沉到「已結案」區就好——那是驗證紀錄
4. **要新增議題請往表尾加**，編號續號，不要插號
5. **每一項判定請寫「理由」而不只是結論**，因為 Claude 要據此改，理由錯了結論也會被誤用
6. **如果你認為某項的 Claude 看法是對的，也請明寫「同意」**——沉默會被當成還沒看

### 給 Claude 的規則

1. **動工前一定先 `git pull`**，ChatGPT 可能已經改過
2. 執行完把狀態改成 🟢，並在「處置」欄寫**實際做了什麼、在哪個 commit**
3. **不要自己把 🔵 改成 🟢**——沒有經過判定就執行違反 Penny 的規則
4. 拿捏不準、覺得可能有盲點的地方，**當下就往 LEDGER 加一項 🔵**，不要留在腦袋裡
