## §1 這個專案要做什麼

### 1.1 一句話

把三個 repo 裡所有的 AI KOL 人設，做成一個**放在 Railway 上的公開型錄網站**，
使用者可以把連結直接丟給客戶或合作方，用「翻型錄選人」的方式介紹這些 KOL。

### 1.2 讀者與他們要做的動作

| 讀者 | 他打開連結之後想做的事 | 他停留多久 |
|---|---|---|
| **潛在客戶（主要）** | 「有沒有適合我品牌的人？」→ 挑出 1–3 位 | 首頁 30 秒，人設頁 2 分鐘 |
| 已成交客戶 | 確認我買的這位長什麼樣、發過什麼 | 直接看單一人設頁 |
| 合作方／通路 | 這個團隊做得出什麼水準的東西 | 掃過首頁與 2–3 個案例 |
| 使用者本人對外簡報 | 開著它講 | 需要能投影、字要夠大 |

★ **這決定了整個設計**：型錄的第一個功能是**幫人淘汰**（快速排除不適合的），
第二個才是說服。所以首頁要能篩、人設頁要有真素材、案例頁要有數字。

### 1.3 這不是什麼（刻意排除，避免覆核往錯方向給建議）

- ❌ **不是內部儀表板。** `Buildup_KOL/dashboard/`（React + Vite）已經是內部評估工具了，那個不對外。
- ❌ **不是成效報告站。** `showgame-kol/railway/` 與 `railway-report/` 是給管理層看去留判斷的，整站有密碼，跟本站的讀者完全不同。
- ❌ **不做互動查詢服務**（例如「貼一批關鍵字吐出分派結果」）。型錄是唯讀的展示品。
- ❌ **不放製作機密**：prompt、Soul ID、模型名稱、credits、重做輪數，一律不對外。

## §2 我的規劃

### 2.1 現況盤點（**這些數字全部由程式現算，不是我手寫的**）

產生程式：`catalog/tools/scan_inventory.mjs` → 輸出 `catalog/data/inventory.json`
重跑方式：`node catalog/tools/scan_inventory.mjs --print`
**任何 `.md` 裡的數字若與那份 JSON 不符，那是 bug，請直接開一條議題。**

```
人設 42 位（重複收錄 16、欄位互斥 4、標為已上線 5）
分區：可撐一頁 20 / 素材不足 4 / 只有文字 18
素材：圖 727 張 2,434.8 MB（平均 3.35 MB）
      影片 187 支 2,606.2 MB（平均 13.94 MB）
      合計 5,041 MB
```

三個 repo 的分工與各自持有量：

| repo | 角色 | 人設數 | 圖 | 影片 |
|---|---|---|---|---|
| `Virtual_KOL_Studio` | 人設 canon（identity／外觀／視覺規格） | 30 | 357 | 42 |
| `showgame-kol` | 實戰線（已發布素材、平台連結、Metricool 成效） | 11 | 259 | 94 |
| `Buildup_KOL` | 評估工具線（話題適配度、評分） | 24 | 111 | 51 |

**42 位是聯集去重之後的數字**（16 位同時存在於兩個 repo）。

### 2.2 站的形式：三層，靜態產生

```
第 1 層  首頁型錄牆（Grid Wall）
         42 張卡 → 大圖為主、每張只有 3 個資訊：名字／一句話定位／類型標籤
         上方一排篩選器：類型・語言・地區・年齡帶・有無影片案例・可上線／籌備中
         目的：30 秒內淘汰掉 90%

第 2 層  人設頁（一人一頁，42 頁）
         ┌ Hero 滿版直式大圖 ＋ 名字 ＋ 一句話定位 ＋ 3–5 個標籤
         ├ 基本資料條（年齡・族裔・所在地・語言・平台）
         ├ 圖庫 6–9 張（瀑布流，點開放大）
         ├ 影片案例 1–3 支（內嵌播放，直式 9:16）
         ├ 內容主題 3–5 條 ＋ 語氣範例 2 則（**用真的發過的貼文文案**）
         └ 邊界說明：這位不接什麼（紅線）
         目的：2 分鐘內判斷「像不像我要的人」

第 3 層  案例頁（只給有實際發布紀錄的人設）
         單篇貼文的完整樣貌：素材＋文案＋發了哪些平台＋曝光數字＋可信度標示
         目的：證明這不是只有圖，是真的在運作的帳號
```

**技術選擇：靜態產生（build 出純 HTML）＋ Node 零依賴 server。**

| 為什麼不用 React SPA | |
|---|---|
| 42 張卡 ＋ 42 頁是**固定內容**，不需要 runtime 狀態管理 | |
| 型錄要能被截圖、被投影、被存成 PDF 給客戶 | |
| `showgame-kol/railway/` 已經用這個模式部署成功過，踩過的坑都有紀錄可沿用 | |
| 篩選器用原生 JS 對 DOM 加 class 就夠，不值得為它上框架 | |

**唯一的相依是 build 階段的圖片處理**（縮圖／轉檔），跑完就不需要了。

### 2.3 放什麼資料（逐欄，含來源與「為什麼客戶要看這個」）

| 欄位 | 從哪來 | 客戶為什麼要看 | 型錄裡的位置 |
|---|---|---|---|
| 名字／中文名／handle | `profile.json` `identity` | 識別 | 卡片＋Hero |
| **一句話定位** | 新寫（從 `character.md` 濃縮） | **這是篩選的唯一依據** | 卡片＋Hero |
| 類型（beauty／fitness／travel…） | `profile.json` `meta.category` | 第一層篩選 | 卡片標籤＋篩選器 |
| 年齡・族裔・所在地・語言數 | `identity` | 在地化與市場適配 | 基本資料條＋篩選器 |
| 內容主題 3–5 條 | `content_style.md` | 判斷跟品牌搭不搭 | 人設頁中段 |
| **語氣範例 2 則** | **真的發過的貼文文案**（`social media/*/schedule.md`） | 判斷語感，比形容詞有用 | 人設頁中段 |
| Hero 圖 ×1 | `images/` 挑選 | 第一印象 | Hero |
| 圖庫 6–9 張 | `images/` 挑選 | **證明同一張臉能重現**（這是本專案最難的技術點，也是最強的賣點） | 人設頁 |
| 影片案例 1–3 支 | `videos/` ＋ 已發布平台連結 | 證明會動、會講話 | 人設頁 |
| 已上線平台 | `showgame-kol/CLAUDE.md` 帳號表 ＋ Metricool | 可信度 | 基本資料條 |
| 成效數字 | Metricool 實查（**只有 6 位有**） | 證明不是只有作品集 | 案例頁 |
| 這位不接什麼 | `kol-redline-check` 規則 | 避免客戶提出做不到的需求，也避免我們踩雷 | 人設頁底 |
| 狀態：可上線／籌備中 | 見 CC-01（**不能直接吃 profile.json**） | 管理期待 | 卡片角標 |

### 2.4 刻意不放的（型錄的克制比豐富重要）

| 不放 | 為什麼 |
|---|---|
| prompt、Soul ID、模型名、訓練張數、credits | 製作機密。而且客戶一看到「這是 AI 生的圖」的技術細節，注意力就從「這個人適合我嗎」跑掉了 |
| 內部代號（`G3`／`D6`／`KC-01`） | 使用者已明文禁止對外文件用內部代號——他還得回頭解釋那段對話 |
| 未滿 72 小時的成效數字 | 本專案已量過：同一則貼文隔一天曝光成長 +76%～+298%。早看會誤導 |
| 沒發過任何內容的人設的「預估數字」 | 已犯過一次：拿別人的數字填進空人設的表格，被使用者一眼看破 |
| 重做輪數、被退稿紀錄 | 內部檢討用，對外是自曝短處 |
| 每位人設的完整圖庫（全部 727 張） | 型錄要挑過。全放等於沒挑，而且會暴露品質不均 |

### 2.5 素材策略：**5 GB 不可能原樣上 Railway**，所以要「挑 → 轉 → 外放」

這是整個規劃最硬的技術限制，先把數字攤開：

| | 現況 | 型錄實際需要 |
|---|---|---|
| 圖 | 727 張・2,435 MB・平均 3.35 MB | **挑 ~230 張**（20 位 × (1 Hero + 8 圖) + 少量案例圖） |
| 影片 | 187 支・2,606 MB・平均 13.94 MB | **挑 ~45 支**（可撐頁的人設每人 1–3 支） |

**三段處理：**

1. **挑（curate）**——不是全放。每位人設 1 張 Hero ＋ 6–9 張圖庫 ＋ 1–3 支影片。
   挑選規則寫成清單，由使用者過目（**挑哪一張是審美判斷，見 §0.4**）。
2. **轉（derive）**——產生三種衍生檔，原圖永遠不上線：
   | 衍生檔 | 規格 | 預估單檔 | 用在哪 |
   |---|---|---|---|
   | thumb | 寬 400px JPEG q78 | ~40 KB | 首頁卡片 |
   | web | 長邊 1440px JPEG q82 | ~220 KB | 人設頁圖庫 |
   | poster | 影片首幀，寬 720px JPEG | ~50 KB | 影片播放前 |
   | video | 720×1280 H.264 CRF 26 ＋ AAC 96k | ~1.5–2.5 MB | 人設頁影片 |

   預估總量：`230×0.26 MB + 45×0.05 MB + 45×2 MB ≈ **152 MB**`
   → **5,041 MB 壓到約 152 MB，縮 33 倍。**

3. **外放（host）**——三個做法，我的立場在最後一欄：

   | | 做法 | 好處 | 代價 | 我的立場 |
   |---|---|---|---|---|
   | 甲 | 衍生檔 commit 進 `catalog/assets/`，Railway 直接供應 | 沒有第二個系統、沒有金鑰、部署即上線 | `.git` 增加約 152 MB（一次性；之後每次換圖再加） | ✅ **建議先走這個** |
   | 乙 | 衍生檔放 Cloudflare R2／S3，站上只放 JSON 與 HTML | `.git` 幾乎不長大、CDN 快 | 多一組金鑰、多一條部署步驟、多一個會忘記更新的地方 | 素材超過 ~500 MB 再換 |
   | 丙 | 影片不自己託管，改嵌入已發布的平台貼文 | 零頻寬、順便證明「真的發出去了」 | 只有 6 位人設有已發布連結；平台改版會壞；嵌入式播放器會拖慢頁面 | 當**補充**不當主力 |

   ★ **走甲的理由不是它最漂亮，是它最少手動步驟。**
   本專案已經因為「要記得的手動步驟」漏過好幾次
   （排程檔少一個區塊整天沒發、字幕版沒換到、紀錄少回填一筆）。
   152 MB 換掉一整條「記得同步到物件儲存」的流程，我認為值得。
   ⚠ 但 `showgame-kol` 的 `.git` 已經 1.8 GB 並且明文禁止影片進 git——
   **本 repo 尚未有那條規則，但這是同一種累積。這一條我想請你判**（KC 待開）。

### 2.6 Railway 部署規劃

沿用 `showgame-kol/railway/` 已驗證成功的模式（同一個 Railway 帳號、同一種 Node 零依賴 server）。

| 設定 | 值 |
|---|---|
| Railway project / service | `kol-catalog` / `catalog-site` |
| Source Repo | `pennyhuang-oss/Virtual_KOL_Studio` |
| Root Directory | `/catalog` |
| Watch Paths | `catalog/**` |
| Networking → 網址的 `→ Port` | **8080** |
| 環境變數 `PORT` | 🛑 **不要加**（讓 Railway 自己注入） |

**這三個坑是實際踩過並寫下來的**（來源：`showgame-kol/railway/README.md`）：

1. Railway 注入 `PORT=8080`，但 Generate Domain 產生的網址預設指到別的埠 → 對不上就一路 502。
   **診斷第一步是看 Deploy Logs 裡程式自己印的 `listening on ____`，不要猜埠號**
   （那次連猜錯兩次才去看 log）。
2. 換 Root Directory 之後 Watch Paths 沒跟著改 → 之後 push 不會重新部署，而且看不出原因。
3. 用 `curl` 反覆檢查同一個網址會拿到沒有 cache-busting 的舊快取，
   看起來像「站掛了」，實際上部署幾小時前就成功了。
   **同一種檢查方法連續拿到一樣的結果時，要換一個來源再驗**（例：改看 status API 或 log）。

**存取控制——這一條跟另外兩個站相反，所以要特別講：**

`showgame-kol` 的兩個站整站 HTTP Basic Auth，因為裡面有各人設的去留判斷。
**本站是要丟給客戶的，所以必須公開。** 我的規劃：

- ✅ 公開，無密碼
- ✅ `X-Robots-Tag: noindex, nofollow` ＋ `robots.txt` 全站 disallow（可以拿到連結的人才看得到，但不進搜尋引擎）
- ✅ 只供應衍生檔（長邊 1440px），**原圖永遠不上線**
- ⚠ 但這代表 42 位 AI KOL 的臉全部可被爬取與再散布。**這一條要使用者裁決**（見 `PP-01`）

## §3 我自己已經知道的問題（先開，不等你發現）

### `CC-01`　🔴 P0：`profile.json` 的 `status` 不能當型錄的真理來源——已實測有三種錯

型錄的卡片要標「可上線／籌備中」。最自然的做法是讀 `profile.json` 的 `meta.status`。

### `CC-04`　🔴 P0：AI 揭露要放在哪裡、講多明白

**我的立場**：要揭露，而且要放在**首頁第一屏**，不是頁尾小字。理由有三個：
1. 它是紅線規則，不是選配。
2. 藏起來然後被客戶自己看出來，比一開始講明傷得多。

### `CC-05`　🟡 152 MB 衍生檔進 git 是不是在重複 `showgame-kol` 的錯

`showgame-kol` 的 `.git` 已經 1.8 GB，並在 2026-08-18 明文禁止影片進 git，
理由是「20 天累積 1.8 GB → 一年 32 GB，git 永久保留每個版本，影片幾乎不能差異壓縮」。

本 repo（`Virtual_KOL_Studio`）**目前沒有那條規則**，而且它已經追蹤了 627 張圖與 42 支影片。
我提議的甲案會再加約 152 MB 的衍生檔，**而且每次換圖／換人設都會再加一份**。

**我的立場**：先走甲（少一條手動步驟的價值大於 152 MB），但**同時**：
- 把 `catalog/assets/` 的體積上限寫成程式檢查（超過就 build 失敗），不要只寫在文件裡
- 上限訂 **300 MB**
- 超過就換乙案（物件儲存）

★ 本專案自己的結論是「寫成文件會再犯，寫成程式不會」——有兩個正例（圖片大小上限、TikTok 解析度上限都是寫成程式之後才真的停止再犯）。所以這個上限我要寫成 build 期的檢查。
**請你判**：300 MB 這個數字有沒有依據，還是我在憑感覺訂？（我承認是憑感覺訂的。）

### `CC-06`　🟡 「語氣範例用真的發過的貼文文案」只有 6 位人設辦得到

我規劃在人設頁放 2 則真實貼文文案，因為那比任何形容詞都更能讓客戶判斷語感。
**但只有 showgame 那 6 位有實際發布紀錄**（有 post id、有平台、有驗證過的 `PUBLISHED` 狀態）。
另外 36 位只有 `content_style.md` 裡的**設計稿**文案。

**我的立場**：兩者都放，但**視覺上要分得出來**——真實發布的標「已發布・平台・日期」，
設計稿的標「示例文案」。**不要讓客戶誤以為 42 位都在營運。**
**請你判**：這樣的區分會不會反而凸顯「大部分還沒上線」？

### `PP-01`　⬜ 需使用者裁決：型錄公開的程度

型錄要丟給客戶，所以不能有密碼。但公開就代表 42 位人設的臉可被任何人爬取與再散布。

| 選項 | 好處 | 代價 |
|---|---|---|
| 甲 完全公開 ＋ noindex | 連結丟過去就能看，零摩擦 | 臉可被爬走 |
| 乙 全站一組帳號密碼（跟另兩個站一樣） | 可控 | 客戶要多一步、會問密碼、體驗差 |

**這是商業決定不是技術決定，我不自己選。** 我的傾向是甲，但要使用者知道代價。
