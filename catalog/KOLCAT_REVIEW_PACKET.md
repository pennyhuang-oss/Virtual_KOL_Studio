## §1 這個專案要做什麼

### 1.1 一句話

把三個 repo 裡所有的 AI KOL 人設，做成一個**放在 Railway 上的公開型錄網站**，
使用者可以把連結直接丟給客戶或合作方，用「翻型錄選人」的方式介紹這些 KOL。

### 1.2 讀者與他們要做的動作

| 讀者 | 他打開連結之後想做的事 | 他停留多久 |
|---|---|---|
| **潛在客戶（主要）** | 「有沒有適合我品牌的人？」→ 挑出 1–3 位 | 首頁 30 秒，人設頁 2 分鐘 |
| 已成交客戶 | 確認我買的這位長什麼樣、發過什麼 | 直接看單一人設頁 |
| 合作方／通路 | 這個團隊做得出什麼水準的東西 | 掃過首頁與 2–3 個案例 |
| 使用者本人對外簡報 | 開著它講 | 需要能投影、字要夠大 |

★ **這決定了整個設計**：型錄的第一個功能是**幫人淘汰**（快速排除不適合的），
第二個才是說服。所以首頁要能篩、人設頁要有真素材、案例頁要有數字。

### 1.3 這不是什麼（刻意排除，避免覆核往錯方向給建議）

- ❌ **不是內部儀表板。** `Buildup_KOL/dashboard/`（React + Vite）已經是內部評估工具了，那個不對外。
- ❌ **不是成效報告站。** `showgame-kol/railway/` 與 `railway-report/` 是給管理層看去留判斷的，整站有密碼，跟本站的讀者完全不同。
- ❌ **不做互動查詢服務**（例如「貼一批關鍵字吐出分派結果」）。型錄是唯讀的展示品。
- ❌ **不放製作機密**：prompt、Soul ID、模型名稱、credits、重做輪數，一律不對外。

### 用實測重算整站總量（取代 R1 的 152 MB 估值）

計畫選集：圖 230 張（每張都要 web ＋ thumb）、影片 45 支（每支都要 mp4 ＋ poster）。
**兩個情境都算**，因為覆核者指出單一估值掩蓋了尾巴：

| 情境 | 圖 web | 圖 thumb | 影片 | poster | **合計** |
|---|---|---|---|---|---|
| 全部取 p50（樂觀） | 17.5 | 4.1 | 77.5 | 2.9 | **102 MB** |
| 全部取 p95（保守） | 43.2 | 9 | 260.5 | 4.8 | **317.5 MB** |

★ **三個從實測看出來、R1 完全沒看到的事實：**

1. **R1 的單檔估值在中位數附近大致對，但尾巴差很多。**
   圖 web 我估 0.22 MB，實測 p50 只有 0.076 MB（**我高估 2.9 倍**）；
   影片我估 2 MB，實測 p50 1.722 MB 很接近，但 **p95 是 5.788 MB，我低估 2.9 倍**。
   → **R1 的 152 MB 剛好落在 p50 與 p95 之間，那是碰巧，不是算對。**

2. **影片是唯一的槓桿，圖根本不是問題。**
   保守情境下影片佔 260.5 MB ／ 317.5 MB ＝ **82%**。
   圖的 web ＋ thumb 加起來只有 52.2 MB。
   → **調圖片畫質省不到東西，調影片時長才會。**

3. **影片大小幾乎完全由時長決定，不是由畫面內容。**
   實測 MB／秒 p50 0.116、p95 0.243，
   而時長分布是 p50 12.1 秒但 max 68 秒。
   位元率實測分布是 0.065 〜 0.358 MB/秒（**5.5 倍差距**），
   最貴的那一支只有 14.8 秒卻轉出 5.285 MB——那是舞蹈片，畫面運動量大。

4. 🛑 **「把片段剪短」救不了尾巴，這一點跟我原本以為的相反。**
   若把型錄影片一律剪到 20 秒以內，45 支的總量是：

   | 用哪個位元率 | 算式 | 合計 |
   |---|---|---|
   | p50 0.116 MB/秒 | 45 × 20 × 0.116 | **104.4 MB** |
   | p95 0.243 MB/秒 | 45 × 20 × 0.243 | **218.7 MB** |
   | max 0.358 MB/秒（全部都是舞蹈片） | 45 × 20 × 0.358 | **322.2 MB** |

   → **剪到 20 秒之後，總量仍然可能是 104.4 MB 到 322.2 MB。**
   決定大小的是**畫面運動量**，那不是我們選得起的——舞蹈與口播就是不一樣貴。

### 2.2 站的形式：兩區型錄牆 ＋ 人設頁（R2 依 `CC-03`／`Q1` 改）

```
第 1 層  型錄牆 —— 明確分兩區，不混合呈現邏輯
         ┌ 上區「可承接」 20 位
         │    完整卡片：大圖 ＋ 名字 ＋ 一句話定位 ＋ 類型標籤
         │
         └ 下區「籌備中」 22 位
              一致的名單呈現（文字列表，不做圖框）
              🛑 不做「無圖的降級卡」——那會看起來像壞掉的完整卡

         區標直接寫出數量：「可承接 20 位 ／ 籌備中 22 位」

第 2 層  人設頁（只有可承接的 20 位有）
         ┌ Hero 直式大圖 ＋ 名字 ＋ 一句話定位 ＋ 3–5 個標籤
         ├ 基本資料條（年齡・族裔・所在地・語言・已上線平台）
         ├ 圖庫 6–9 張
         ├ 影片案例 1–3 支（直式 9:16）
         ├ 內容主題 3–5 條 ＋ 語氣範例 2 則
         ├ 【已發布案例】區塊 —— 有實際發布紀錄的人設才出現
         │    素材 ＋ 文案 ＋ 平台 ＋ 日期 ＋ 曝光數字與可信度標示
         │    每個案例有自己的錨點網址（#case-YYYYMMDD），可以單獨分享
```

| R1 寫的 | 問題 | R2 改成 |
|---|---|---|
| 「首頁 42 張卡」 | 與 §3 `CC-03` 提的「只放 20＋4 位」直接衝突，同一份文件講兩套 | 上區 20 張完整卡，下區 22 位純名單，**沒有 42 張卡** |
| 「20 完整卡 ＋ 4 張無圖降級卡 ＋ 18 位折疊名單」 | 三種呈現邏輯混在一頁 | **兩種**：完整卡／名單。素材 1–7 張的 4 位歸「籌備中」名單 |

**案例改成人設頁裡的區塊，不做獨立第三層**（依 `Q1`)：
只有 6 位有成效數字，獨立一層會造成明顯不對稱。**保留錨點網址**，所以還是可以把單一案例的連結丟給客戶。
等案例數量變多、或出現「跨人設比較」的需求，再拆成獨立頁面。

**技術選擇：靜態產生(build 出純 HTML)＋ Node 零依賴 server。**

| 為什麼不用 React SPA |
|---|
| 20 張卡 ＋ 20 頁是**固定內容**，不需要 runtime 狀態管理 |
| 型錄要能被截圖、被投影、被存成 PDF 給客戶 |
| `showgame-kol/railway/` 已經用這個模式部署成功過，踩過的坑都有紀錄可沿用 |

### 2.5 素材策略（R2 依實測全面改寫）

🛑 **R1 這一節的結論是錯的，而且錯在沒去量就先下結論。**
實測數字與推翻的過程在 §2.1 的「衍生檔的實測大小」那一段（程式產生），這裡只寫改後的做法。

**選集規模（未變）**：圖 230 張(20 位 × (1 Hero ＋ 8 圖） ＋ 案例圖）、影片 45 支。

**三段處理：**

1. **挑(curate)** —— 挑選規則寫成清單交使用者過目。**挑哪一張是審美判斷，不送覆核**(§0.4)。
2. **轉(derive)** —— 產生四種衍生檔，原圖永不上線。規格與實測大小見 §2.1。
   ⚠ 影片濾鏡**鎖長邊不鎖高度**——R1 只鎖高度，母體那 2 支橫式影片(1280×720)會完全不被縮小。已改並實測過。
3. **放(host)** —— 🛑 **圖與影片分開處理，這是 R2 最大的改動：**

   | | 保守情境(p95) | 怎麼放 | 為什麼 |
   |---|---|---|---|
   | **圖**(web ＋ thumb,230 張） | **52.2 MB** | ✅ **commit 進 `catalog/assets/`** | 這個量級一次性進 git 無感，而且換圖只是零星增量。省掉一整條「記得同步到物件儲存」的手動步驟 |
   | **影片 ＋ poster**(45 支） | **265.3 MB** | 🛑 **外放到物件儲存，不進 git** | 量級大一個數量級，**而且上限不可控** |

   **影片為什麼不可控（實測）**：大小由**畫面運動量**決定，不是由時長。
   位元率實測 0.065〜0.358 MB/秒，**5.5 倍差距**——最貴的一支只有 14.8 秒卻轉出 5.285 MB（舞蹈片）。
   所以「把片段剪到 20 秒」救不了尾巴：45 支 × 20 秒的總量仍然是 104〜322 MB,
   取決於選到的是口播還是舞蹈。**那不是我們選得起的。**

   ★ 這正是 `showgame-kol` 2026-08-18 禁止影片進 git 的同一個理由
   (「影片幾乎不能差異壓縮，重剪一次就再加一份完整大小」),
   而 R1 把它寫成「值得換」的取捨。**量完之後那個取捨不成立。**

**上限怎麼訂（取代 R1 那個憑感覺的 300 MB)：**

R1 訂「工作目錄 300 MB」，兩頭都不對——保守情境 317.5 MB 就超過它，
而它管的是某一刻的目錄大小，**管不到 git 歷史的累積**。改成三個分項，**全部做成 build 期檢查**：

| 檢查 | 上限 | 依據 |
|---|---|---|
| `catalog/assets/` 圖片總量 | **80 MB** | 實測 p95 52.2 MB × 1.5 倍餘裕 |
| 單張圖 | **0.4 MB** | 實測 max 0.206 MB × 約 2 倍 |
| **本 repo 因 KOLCAT 而增加的 git 物件量（年度）** | **150 MB／年** | 這一項才是 `CC-05` 指出的真風險。用 `git count-objects -v` 對照基準線量 |
| 進 git 的影片數 | **0 支** | 硬性，不是上限 |

⚠ **上面每個數字仍然需要覆核**：80 MB 與 150 MB／年是我從實測值推的，
但「1.5 倍餘裕」與「一年可接受多少」都還是判斷，不是量出來的。**這一條請你判**(`CC-05` 續）。

★ 本專案的結論是「寫成文件會再犯，寫成程式不會」——已有兩個正例（圖片大小上限、TikTok 解析度上限都是寫成程式之後才真的停止再犯）。
**所以這四項一律寫成 build 期檢查，超過就讓 build 失敗，不印警告然後繼續。**


### 2.5b 型錄專用狀態清冊（R2 依 `CC-01` 改，取代 R1 的 override 檔）

R1 提「`status_override.json` ＋ 缺值默認籌備中」。覆核者不同意，理由是
**它會變成第二個人工且可能過期的真理來源，而默認值掩蓋了資料缺漏**。這個批評成立，改法：

檔案：`catalog/data/persona_status.json`。**42 位全部必須明確列出，缺任何一位就讓 build 失敗**——
沒有默認值，所以「漏填」會被抓到，不會被靜靜當成籌備中。

| 欄位 | 內容 |
|---|---|
| `status` | `可承接` / `籌備中` / `停用` / `待確認` ——**四種，沒有第五種也沒有空值** |
| `as_of` | 這個判定是哪一天做的 |
| `basis` | 依據什麼判的（例：`Metricool 實查 56 篇 provider 貼文`／`CLAUDE.md 帳號表 2026-08-19 停用`） |
| `owner` | 誰負責維護這一列（`KC-03` 要求） |
| `expires_after_days` | 超過幾天沒更新就自動降級成 `待確認`（`KC-03` 要求） |

**`待確認` 與 `停用` 都不出現在型錄的「可承接」區**，也不會顯示 handle 與平台連結。

★ **為什麼一定要有這一份**（R1 的 `CC-01` 已實測，這裡不重述細節）：
`profile.json` 的 `meta.status` 有三種錯——`rafael-costa` 停用了還寫「正在經營中」、
`kai-luo` 的欄位不存在、`leon-lim` 整個檔案不存在。**直接吃那個欄位會把停用的賣給客戶。**

⚠ **覆核者原本的疑慮還沒被解掉**：這份清冊自己也會過期。
`expires_after_days` 是我的解法（過期自動降級成 `待確認`，而 `待確認` 不會被賣出去），
**但那個天數要訂幾天我沒有依據。這一條請你判。**

### 2.5c 🛑 對外資產的權利、合規與生命週期治理（R2 新增，`Q5` ＋ `KC-01`）

**這是我整份 R1 完全漏掉的一個類別，不是漏掉細節。** 覆核者的原話是
「在公開展示前，需要知道每張圖、影片、文案、音樂、商標及平台嵌入是否有展示權，
誰批准上線，何時必須下架，以及素材或狀態過期時由誰更新；`noindex` 不能取代這一層治理」。

**我接受，而且我認為它比我原本列的任何一條 P0 都更前面**——因為前面那些做錯了是改一版，
這一條做錯了是已經公開出去的東西要回收。

每一件進 build 的對外素材都要有這五欄，**任何一欄是空的就不准進 build**：

| 欄位 | 內容 | 為什麼 |
|---|---|---|
| `source` | 這個檔案是哪裡來的（哪個 repo、哪個生成批次、或第三方） | 沒有來源就無法判斷有沒有展示權 |
| `rights` | `自製可公開` / `自製僅內部` / `第三方授權（附範圍）` / `未確認` | `未確認` 一律擋 |
| `approved_by` ＋ `approved_at` | 誰批准這一件對外 | 型錄是對外文件，要有人負責 |
| `takedown_condition` | 什麼情況必須下架 | 例：某人設停止經營、某客戶合約結束 |
| `risk_flags` | 音樂／商標／肖像近似／可辨識場所 | 這幾類是最容易出事的 |

**已知需要特別查的四項（我還沒查，不要當成查過了）：**

1. **配樂**——影片裡有沒有配樂、那些配樂哪來的。
   本專案已知一件相關事實：TikTok 的商用音樂庫配樂**是發布時由平台端套上的、不會混進影片檔**，
   所以那一類不會出現在型錄的檔案裡；但**自己剪進去的配樂會**。
2. **人設的臉與真人的近似度**——`Virtual_KOL_Studio` 的建模流程用了 58 張真人參考圖
   （`review/batch3_face_refs/`）。那些**參考圖本身不會出現在型錄**，
   但「生成結果與某個真人像不像」是另一個問題，而且本專案已經發生過「這張臉跟另一個人設太像」被退。
3. **可辨識的場所與商標**——圖裡的店招、飯店、車輛、包裝。
4. **平台嵌入**——若走「嵌入已發布貼文」那條路，等於把第三方播放器與追蹤碼放進型錄。

⚠ **這一節目前只有結構，沒有任何一件素材真的被查過。**
**我的立場是：這一層沒做完就不要上線，即使版面都定案了。** 請你確認這個優先序對不對。

### 2.5d 發布驗收門檻（R2 新增，`KC-04`）

覆核者指出 R1 有部署方法與素材規格，但**沒有定義「什麼條件下可以公開」**，
所以錯誤連結、超量資產、手機播放失敗、`noindex` 漏設都可能直接上線。接受。

**做成一支 `catalog/tools/preflight.mjs`，全部通過才准部署。任何一項失敗就 exit 非零。**

| 檢查 | 內容 |
|---|---|
| 資料 schema | `catalog.json` 每個欄位型別正確、必填欄不得為空 |
| 狀態清冊完整性 | 42 位全部在 `persona_status.json` 裡，且無 `as_of` 過期 |
| 權利欄完整性 | 每件素材的五欄（§2.5c）都有值，`rights` 不得為 `未確認` |
| slug 唯一性 | 沒有重複的人設網址 |
| 資產存在性 | `catalog.json` 引用的每個檔案都真的存在 |
| 資產容量 | §2.5 那四項分項上限 |
| 連結 | 站內連結不得 404；站外連結（平台帳號）逐一檢查可達 |
| HTTP headers | `X-Robots-Tag: noindex, nofollow` 與 `robots.txt` 確實生效 |
| 手機版面 | 主要尺寸（375／390／414 寬）下不得有橫向溢出 |
| 影片播放 | 每支影片能被真的播放（不是只檢查檔案存在） |

⚠ **這支的每一項都要自己先被驗過會失敗**——本專案的經驗是「檢查程式寫了但從來沒測過它會不會擋」
已經踩過（`metricool.mjs` 的刪除功能被寫成「清不掉」，實際上是**從來沒試過**）。
所以每一項都要有一個故意弄壞的對抗測試。

### 2.6 Railway 部署規劃

沿用 `showgame-kol/railway/` 已驗證成功的模式（同一個 Railway 帳號、同一種 Node 零依賴 server）。

| 設定 | 值 |
|---|---|
| Railway project / service | `kol-catalog` / `catalog-site` |
| Source Repo | `pennyhuang-oss/Virtual_KOL_Studio` |
| Root Directory | `/catalog` |
| Watch Paths | `catalog/**` |
| Networking → 網址的 `→ Port` | **8080** |
| 環境變數 `PORT` | 🛑 **不要加**（讓 Railway 自己注入） |

**這三個坑是實際踩過並寫下來的**（來源：`showgame-kol/railway/README.md`）：

1. Railway 注入 `PORT=8080`，但 Generate Domain 產生的網址預設指到別的埠 → 對不上就一路 502。
   **診斷第一步是看 Deploy Logs 裡程式自己印的 `listening on ____`，不要猜埠號**
   （那次連猜錯兩次才去看 log）。
2. 換 Root Directory 之後 Watch Paths 沒跟著改 → 之後 push 不會重新部署，而且看不出原因。
3. 用 `curl` 反覆檢查同一個網址會拿到沒有 cache-busting 的舊快取，
   看起來像「站掛了」，實際上部署幾小時前就成功了。
   **同一種檢查方法連續拿到一樣的結果時，要換一個來源再驗**（例：改看 status API 或 log）。

**存取控制——這一條跟另外兩個站相反，所以要特別講：**

`showgame-kol` 的兩個站整站 HTTP Basic Auth，因為裡面有各人設的去留判斷。
**本站是要丟給客戶的，所以必須公開。** 我的規劃：

- ✅ 公開，無密碼
- ✅ `X-Robots-Tag: noindex, nofollow` ＋ `robots.txt` 全站 disallow（可以拿到連結的人才看得到，但不進搜尋引擎）
- ✅ 只供應衍生檔（長邊 1440px），**原圖永遠不上線**

**同一位人設出現在兩個 repo 時，欄位級的真理來源（這是我的立場，不是定案）：**

Q9：三個數字要分開處理。第一，`expires_after_days` 是風險政策，不存在從檔案大小般直接量出的唯一答案；應依狀態分級，取「來源預定更新週期」與「業務能容忍錯誤狀態存在多久」兩者較短者，可承接狀態最嚴，停用狀態因過期只會少賣而不會錯賣，可採事件驅動更新而不必套同一 TTL。第二，80 MB 不應由 p95 × 1.5 決定；完成 `selection.json` 後可全量轉檔得到確切基準，再以「基準＋下一次架構覆核前允許新增或替換的實際數量 × 單檔門檻」推導，並確認不突破部署、clone 時間或 repo 政策。第三，150 MB／年目前就是判斷，應先用每次更新新增的 Git 物件量 × 預期更新次數建立年度模型，再由可接受的 clone／部署時間或儲存成本反推上限；在沒有更新實績與操作目標前，150 MB 應標成暫定觀察線而不是 hard fail。結論：TTL 與年度上限本質上含政策判斷，但必須寫明風險容忍與操作目標；80 MB 則可以在全選集完成後直接重算，不需要猜餘裕倍數。

Q10：仍缺一整類「無障礙與替代內容」。目前只驗手機寬度與影片能否播放，沒有處理語意結構、鍵盤操作、焦點、圖片替代文字、影片字幕／逐字稿、頁面語言、縮放與動態偏好；這些是可驗證的交付品質，不是配色或美感判斷。
