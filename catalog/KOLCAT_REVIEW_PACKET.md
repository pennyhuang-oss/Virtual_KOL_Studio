## §1 這個專案要做什麼

### 1.1 一句話

把三個 repo 裡所有的 AI KOL 人設，做成一個**放在 Railway 上的公開型錄網站**，
使用者可以把連結直接丟給客戶或合作方，用「翻型錄選人」的方式介紹這些 KOL。

### 1.2 讀者與他們要做的動作

| 讀者 | 他打開連結之後想做的事 | 他停留多久 |
|---|---|---|
| **潛在客戶（主要）** | 「有沒有適合我品牌的人？」→ 挑出 1–3 位 | 首頁 30 秒，人設頁 2 分鐘 |
| 已成交客戶 | 確認我買的這位長什麼樣、發過什麼 | 直接看單一人設頁 |
| 合作方／通路 | 這個團隊做得出什麼水準的東西 | 掃過首頁與 2–3 個案例 |
| 使用者本人對外簡報 | 開著它講 | 需要能投影、字要夠大 |

★ **這決定了整個設計**：型錄的第一個功能是**幫人淘汰**（快速排除不適合的），
第二個才是說服。所以首頁要能篩、人設頁要有真素材、案例頁要有數字。

### 1.3 這不是什麼（刻意排除，避免覆核往錯方向給建議）

- ❌ **不是內部儀表板。** `Buildup_KOL/dashboard/`（React + Vite）已經是內部評估工具了，那個不對外。
- ❌ **不是成效報告站。** `showgame-kol/railway/` 與 `railway-report/` 是給管理層看去留判斷的，整站有密碼，跟本站的讀者完全不同。
- ❌ **不做互動查詢服務**（例如「貼一批關鍵字吐出分派結果」）。型錄是唯讀的展示品。
- ❌ **不放製作機密**：prompt、Soul ID、模型名稱、credits、重做輪數，一律不對外。

### 用實測重算整站總量（取代 R1 的 152 MB 估值）

計畫選集：圖 230 張（每張都要 web ＋ thumb）、影片 45 支（每支都要 mp4 ＋ poster）。
**兩個情境都算**，因為覆核者指出單一估值掩蓋了尾巴：

| 情境 | 圖 web | 圖 thumb | 影片 | poster | **合計** |
|---|---|---|---|---|---|
| 全部取 p50（樂觀） | 17.5 | 4.1 | 77.5 | 2.9 | **102 MB** |
| 全部取 p95（保守） | 43.2 | 9 | 260.5 | 4.8 | **317.5 MB** |

★ **三個從實測看出來、R1 完全沒看到的事實：**

1. **R1 的單檔估值在中位數附近大致對，但尾巴差很多。**
   圖 web 我估 0.22 MB，實測 p50 只有 0.076 MB（**我高估 2.9 倍**）；
   影片我估 2 MB，實測 p50 1.722 MB 很接近，但 **p95 是 5.788 MB，我低估 2.9 倍**。
   → **R1 的 152 MB 剛好落在 p50 與 p95 之間，那是碰巧，不是算對。**

2. **影片是唯一的槓桿，圖根本不是問題。**
   保守情境下影片佔 260.5 MB ／ 317.5 MB ＝ **82%**。
   圖的 web ＋ thumb 加起來只有 52.2 MB。
   → **調圖片畫質省不到東西，調影片時長才會。**

3. **影片大小幾乎完全由時長決定，不是由畫面內容。**
   實測 MB／秒 p50 0.116、p95 0.243，
   而時長分布是 p50 12.1 秒但 max 68 秒。
   位元率實測分布是 0.065 〜 0.358 MB/秒（**5.5 倍差距**），
   最貴的那一支只有 14.8 秒卻轉出 5.285 MB——那是舞蹈片，畫面運動量大。

4. 🛑 **「把片段剪短」救不了尾巴，這一點跟我原本以為的相反。**
   若把型錄影片一律剪到 20 秒以內，45 支的總量是：

   | 用哪個位元率 | 算式 | 合計 |
   |---|---|---|
   | p50 0.116 MB/秒 | 45 × 20 × 0.116 | **104.4 MB** |
   | p95 0.243 MB/秒 | 45 × 20 × 0.243 | **218.7 MB** |
   | max 0.358 MB/秒（全部都是舞蹈片） | 45 × 20 × 0.358 | **322.2 MB** |

   → **剪到 20 秒之後，總量仍然可能是 104.4 MB 到 322.2 MB。**
   決定大小的是**畫面運動量**，那不是我們選得起的——舞蹈與口播就是不一樣貴。

### 2.5 素材策略（R2 依實測全面改寫）

🛑 **R1 這一節的結論是錯的，而且錯在沒去量就先下結論。**
實測數字與推翻的過程在 §2.1 的「衍生檔的實測大小」那一段（程式產生），這裡只寫改後的做法。

**選集規模（未變）**：圖 230 張(20 位 × (1 Hero ＋ 8 圖） ＋ 案例圖）、影片 45 支。

**三段處理：**

1. **挑(curate)** —— 挑選規則寫成清單交使用者過目。**挑哪一張是審美判斷，不送覆核**(§0.4)。
2. **轉(derive)** —— 產生四種衍生檔，原圖永不上線。規格與實測大小見 §2.1。
   ⚠ 影片濾鏡**鎖長邊不鎖高度**——R1 只鎖高度，母體那 2 支橫式影片(1280×720)會完全不被縮小。已改並實測過。
3. **放(host)** —— 🛑 **圖與影片分開處理，這是 R2 最大的改動：**

   | | 保守情境(p95) | 怎麼放 | 為什麼 |
   |---|---|---|---|
   | **圖**(web ＋ thumb,230 張） | **52.2 MB** | ✅ **commit 進 `catalog/assets/`** | 這個量級一次性進 git 無感，而且換圖只是零星增量。省掉一整條「記得同步到物件儲存」的手動步驟 |
   | **影片 ＋ poster**(45 支） | **265.3 MB** | 🛑 **外放到物件儲存，不進 git** | 量級大一個數量級，**而且上限不可控** |

   **影片為什麼不可控（實測）**：大小由**畫面運動量**決定，不是由時長。
   位元率實測 0.065〜0.358 MB/秒，**5.5 倍差距**——最貴的一支只有 14.8 秒卻轉出 5.285 MB（舞蹈片）。
   所以「把片段剪到 20 秒」救不了尾巴：45 支 × 20 秒的總量仍然是 104〜322 MB,
   取決於選到的是口播還是舞蹈。**那不是我們選得起的。**

   ★ 這正是 `showgame-kol` 2026-08-18 禁止影片進 git 的同一個理由
   (「影片幾乎不能差異壓縮，重剪一次就再加一份完整大小」),
   而 R1 把它寫成「值得換」的取捨。**量完之後那個取捨不成立。**

**上限怎麼訂（取代 R1 那個憑感覺的 300 MB)：**

R1 訂「工作目錄 300 MB」，兩頭都不對——保守情境 317.5 MB 就超過它，
而它管的是某一刻的目錄大小，**管不到 git 歷史的累積**。改成三個分項，**全部做成 build 期檢查**：

**R3 依覆核者裁決改：只有量得出來的當 hard fail，判斷來的先當觀察線。**
它的理由是「80 MB 與 150 MB／年尚不能直接當硬失敗門檻」——因為那兩個數字還沒有基準可算。

| 檢查 | 值 | hard fail 還是警告 | 依據 |
|---|---|---|---|
| 進 git 的影片數 | **0 支** | 🛑 **hard fail** | 硬性規則，不是上限 |
| 單張圖 | **0.4 MB** | 🛑 **hard fail** | 實測 max 0.206 MB，這個門檻量得出來 |
| `catalog/assets/` 圖片總量 | 暫定 80 MB | ⚠️ **只記錄＋警告** | **`selection.json` 完成後全量轉檔重算基準**，那時才轉成 hard fail |
| KOLCAT 造成的 git 物件年度成長 | 暫定 150 MB／年 | ⚠️ **只記錄＋警告** | **先用「每次更新新增的物件量 × 預期更新次數」建年度模型**，再從可接受的 clone／部署時間反推 |

★ **這一輪學到的方法論**（覆核者 `Q9` 的裁決，值得記下來）：

| 這個數字 | 能不能量出來 | 所以怎麼訂 |
|---|---|---|
| 單檔上限 | ✅ 能（全量轉檔就有確切基準） | **量完再訂，不要猜餘裕倍數** |
| 資料夾總量上限 | ✅ 能（基準 ＋ 下次架構覆核前允許新增的數量 × 單檔門檻） | 同上 |
| 狀態的 `expires_after_days` | ❌ **不能**，那是風險政策 | 取「來源預定更新週期」與「業務能容忍錯誤狀態存在多久」**兩者較短** |
| git 年度成長上限 | ❌ 目前不能 | 先建模型，再從 clone／部署時間或儲存成本反推 |

🛑 **關鍵區分**：`expires_after_days` 與年度上限**本質上含政策判斷，不可能量出唯一答案**——
但**必須寫明風險容忍與操作目標**，不能像 R1 的 300 MB 那樣憑感覺給一個數字然後當門檻。
**「是判斷」跟「憑感覺」不是同一件事**：前者寫得出依據什麼判斷，後者沒有依據。

★ 本專案的結論是「寫成文件會再犯，寫成程式不會」——已有兩個正例（圖片大小上限、TikTok 解析度上限都是寫成程式之後才真的停止再犯）。
**所以這四項一律寫成 build 期檢查，超過就讓 build 失敗，不印警告然後繼續。**

### B. 五題指定問題

Q11：分工方向對，但程式應做「可稽核的候選整理」，不能做不可逆的審美淘汰。程式可以排除已作廢、缺檔、格式不合、權利不准公開與完全重複的素材，並用近似度把連拍／同構圖分群、檢查鏡別與場景覆蓋；不要只因檔名連號就刪除，也不要讓 15–20 張 shortlist 成為看不到完整合格池的黑箱。使用者應能查看全部合格素材、知道每件被排除或分群的原因並覆寫 shortlist，最後 9 張只能由人工決定；程式再驗最終數量、重複度與必要覆蓋，不替人決定哪張最好。

Q12：可以共用的是同一不可變生成批次的 `source`、相同授權文件與範圍下的 `rights`、人設層級的基本臉部比對，以及明確涵蓋一組 asset IDs／雜湊值的整批批准與下架條件。必須逐件檢查的是畫面中的商標、店招、場所、第三方人物與文字，影片內嵌配樂／聲音，以及每個平台貼文嵌入；臉部雖可共用人設級結論，每件入選素材仍要做異常近似的快速例外檢查。實作上用 inheritance：批次／人設層提供預設值，素材層只記例外，但 build 必須展開成每件素材的有效值並留下來源鏈。`risk_flags` 空白不能等於已安全，必須區分「已覆核且無旗標」與「尚未覆核」。

Q13：存取模型要現在決定，供應商可以稍後在相同介面下替換。建議用 private-by-default 的 R2 或 S3 類物件儲存，物件不提供永久公開網址，由型錄後端在通過頁面授權後簽發短效媒體網址或經授權代理；這樣 PP-01 最後選公開、密碼或客戶 token 都能共用同一條邊界。Railway volume 會把影片傳輸、Range 支援與服務生命週期綁在單一服務；平台嵌入則無法服從本站的客戶級撤銷，兩者都不適合作主存放。不可先發布公開物件網址再期待日後補鎖，因為網址可能已被分享或快取；不可猜的檔名也不是存取控制。

Q14：分兩類。固定案例數字是「在某日觀測到的歷史事實」，可以持續顯示，但統計期間與 `as_of` 必須和數字放在一起；「過去 30 天發布 N 篇」是滾動營運摘要，快照過期後就不再代表現在，應隱藏該數字並顯示中性的「最新營運資料更新中」，不能用很舊的日期繼續充當當期能力。Metricool API 快照應另存查詢期間、平台範圍、抓取時間與來源；API 失敗時不得靜默沿用已過期快照。

Q15：還缺一整類「前端效能、媒體傳輸與頻寬成本治理」。目前量過的是資產檔案大小，尚未定義客戶開首頁或人設頁實際下載多少、圖片是否 responsive／lazy-load、影片是否預載、物件儲存是否支援 Range 與快取、慢速網路下的失敗行為，以及公開後被 hotlink 或大量抓取時的流量與成本上限；這些會直接決定 30 秒挑人的目標能否成立，不是版面美感。
